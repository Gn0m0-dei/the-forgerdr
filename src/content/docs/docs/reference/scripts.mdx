The forgerdr talks to the herdr app through its two command-line tools: `herdr-app do` for the window (spaces, tabs, the focus) and `hc` for the terminals and agents in it. The fan-outs and the agent dispatch work only inside a terminal of the app (`HC_TERMINAL_ID` set); outside it, the worktree hook still makes and removes plain git worktrees. New tabs and spaces open without taking the focus unless the command is about what you look at next.

The scripts are plain bash over `herdr-app`, `hc` and `jq`:

```bash
bin/forge-worktree.sh  [--plan] [--repo PATH]... [--base BRANCH] [--dev COMMAND] [--no-dev] [--port-base N] [--auto] [--no-agent] [--no-submodules] [--branch NAME --title TEXT | --kind KIND --title TEXT] <item>...
bin/forge-start.sh     indexed|index|unindex <dir>
bin/forge-review.sh    [--cwd PATH] [--mod NAME] [--no-agent] <pr-url>...
bin/forge-security.sh  launch [--cwd PATH] [--mod NAME] [--title TITLE] [--item ID] [--scope TEXT] [--report-to ADDRESS] [--no-agent]
bin/forge-session.sh   [--cwd PATH] [--no-agent] [--no-focus] --title TITLE <prompt>
bin/forge-session.sh   [--cwd PATH] [--no-agent] --group NAME --title TITLE <prompt> [--title TITLE <prompt>...]
bin/forge-worktree-remove.sh [--discard | --force] <path>
bin/forge-worktree-remove.sh --plan <folder>
bin/forge-changes.sh    tree <repo>... | diff <folder> | own <folder>
bin/forge-ide.sh        ensure|name|servers <checkout> | stop [--discard] <checkout> | order <checkout> save | dir
bin/forge-ide.sh        editors | open zed|code <path>
bin/forge-setup-keys.sh [--review KEY] [--worktree KEY] [--remove]
bin/forge-update.sh     check | apply [--detach]
bin/forge-herdr-install.sh [--dev [--watch]] [--remove] [--force] [--switch]
```

They print one JSON line per worktree, tab or pull request.

## Worktrees

`forge-worktree.sh` makes each worktree where the app keeps its own (`worktrees.directory` in the app's `settings.json`, `~/.herdr/worktrees` by default), so the app's Open and Remove worktree see them. `forge-worktree-remove.sh` removes one the way the app does: its spaces closed first, its branch kept.

- It refuses uncommitted work and a space where an agent is at work. `--discard` throws the uncommitted work away and still refuses an agent at work; `--force` does both.
- It refuses too while the worktree's ttt in the [IDE panel](../../herdr-app/ide/) holds unsaved files, naming them, or while that ttt's state cannot be read; `--discard` and `--force` let it go, and the ttt is stopped before git removes the folder.
- A new worktree gets its git submodules filled, each cloned anew for it; `--no-submodules` skips it. git refuses to remove a worktree with submodules, so the script looks inside each one (its uncommitted files, and its commits no remote has, on a branch, under a tag or in a stash) and forces git only when there is none; `--plan` answers `forced` and names the submodules that hold work.
- An id alone is completed with the forge's backlog before the item is told external.
- The ignored env files are copied into a new worktree only where no symlink its branch carries stands in their way, so a branch cannot send them outside the worktree.
- What the scripts cannot guess (which repositories an item touches in a multi-repo workspace, which `dev:<app>` script of a monorepo) the skills decide and pass as flags.
- `--kind` and `--title` before an item name its branch without asking the provider, from the kind, the item's id (a URL, `#12`, `AB#12`, `12`, `EXT-12` or `""` for none) and the title. The kinds are `feature`, `fix`, `chore` and `release` from the base, and `hotfix` from the production branch.
- A name git would refuse is refused in the plan, and an item of an external backlog never reuses the branch of the repository's own item with the same number.
- Each dev server gets the first port from `--port-base` (3000) that nothing listens on.
- `--plan` says what a run would make, and makes nothing.

## Indexing a forge

`forge-start.sh index <dir>` indexes the forge a directory is of: the [parent folder of repositories](../../way-of-working/parent-folders/#index-the-forge-first) it is or works with, else its repository. Each repository of a parent folder records the folder in its own git config (`forgerdr.workspace`), and the code of the whole forge is indexed as one codebase-memory project, when that program is installed. `indexed` answers how it stands (`state`: `none`, `indexing` or `ready`, how many `repos` and how many `joined`, the code index's `project`, and what `failed` in its last run); `unindex` leaves the repositories on their own again and keeps the code index's project.

## What the Changes panel reads

`forge-changes.sh` is what the [Changes panel](../../herdr-app/changes/) reads, and it only reads: your index, HEAD and stash are never touched, and nothing is written under `.git`.

- `tree <repo>...` answers each repository's checkouts as JSON, the main one first, with the files each changed; a git submodule is listed only while it holds changes.
- `diff <folder>` prints the diff of the checkout a folder is in, from its HEAD to what it holds, then its new files, each shown whole.
- A long diff is cut at `FORGE_CHANGES_DIFF_MAX` lines (20000) or `FORGE_CHANGES_DIFF_BYTES` (4 MiB), a line past 4000 characters is cut too, and past `FORGE_CHANGES_NEW_MAX` new files (400) the rest are left out: each cut says so in the diff's last line.
- A file git cannot read (no permission, a pipe, a folder with a repository of its own or one that cannot be entered) is left out with a line `\ forgerdr: not shown: <path>`, and hides no other.
- `own <folder>` makes the folder the panel keeps its comments in yours alone.

## What the IDE panel runs

`forge-ide.sh` is what the [IDE panel](../../herdr-app/ide/) runs: one ttt per checkout, run by herdr-core as a terminal of its own named after the checkout's path, which lives on until it is stopped. `ensure`, `servers` and `editors` answer in JSON; `name`, `order` and `dir` print one line. Every path must be absolute.

- `name <checkout>` prints the name of the checkout's ttt terminal: `ide-` and a hash of its path.
- `ensure <checkout>` starts the checkout's ttt, or says it runs already. When it cannot, it says why: ttt missing, its version unreadable, older than the 1.14.0 forgerdr needs, or forgerdr's ttt profile not installed.
- `stop [--discard] <checkout>` ends it. It refuses while the ttt holds unsaved files, naming them, or while its state cannot be read, unless `--discard`, which loses them.
- `order <checkout> save` has the ttt save the files it holds unsaved, and prints the order's id, which the ttt's state carries once it has answered.
- `dir` tells the folder the states are kept in, `~/.local/state/forgerdr/ide`, yours alone, and makes it.
- `servers <checkout>` lists the language servers the checkout needs and the machine lacks, with the command that installs each, or the program that command needs when it is missing too.
- `editors` lists the editors installed (Zed, then VS Code), and `open zed|code <path>` opens a folder in one.

## The app's look

`forge-herdr-install.sh` copies the layout, the theme and the mod into the app's home, and the profile the IDE panel runs ttt with into `~/.config/forgerdr/ttt`, apart from your own `~/.config/ttt`. Run again, it updates what it installed and leaves what you changed, naming it (`--force` replaces it, keeping a copy beside it); `--remove` takes it away, the ttt profile with it, except the theme, which any layout may use. `--dev` installs the checkout beside it as `forgerdr-dev`, and `--watch` keeps that copy in step with the checkout until Ctrl-C.

## Updating forgerdr

`forge-update.sh` is what the gnome's [update notice](../../herdr-app/heat-updates-manual/#updates) runs. `check` compares the installed version with the newest release tag of the repository and keeps the release notes in between. `apply` updates the marketplace and the plugin, then runs the new version's `install.sh --update`, which installs or updates what that version needs without asking, and keeps what it says of each piece for the notice. `--detach`, which the app uses, returns once the apply is under way and leaves it running on its own, so closing the notice does not stop it; while one is under way, another is refused.

## Trying a change before installing it

`FORGE_CLAUDE_ARGS`, when set, adds its words to every `claude` the scripts and hooks start: for example `--plugin-dir <checkout>` or `--settings <file>`.
