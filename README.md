A Claude Code plugin for the [herdr](https://herdr.dev) desktop app that carries a whole way of working: coding standards, a terse communication mode, a lazy build philosophy, a persistent-memory protocol, a spec → plan → build flow, an interactive pull request reviewer, a backlog item workflow, and the two things that make a window full of agents worth it: fan out N pull requests into N tabs, fan out N items (backlog items, OpenSpec changes or plain tasks) into N worktrees, each opened as its own space with its env files, its dev server and its own agent.

| Layer | Pieces | What it gives |
|---|---|---|
| Rules, every session | standards · communication · build · memory | one way of coding, talking, building and remembering |
| Design to delivery | `spec` → `plan` → `build` → `ship` | design gate, TDD plan, verified execution, pull request |
| In this session | `review-other` · `review-own` · `debug` · `security` · `research` | interactive and gated, with fresh-context agents where a second pair of eyes helps |
| A session per item, on the herdr app | `workitem` · `worktree` · `review` | one item or many (separated by `\|`; pull requests by spaces); a titled session each, several grouped in new tabs as many panes to a tab as fit, worktrees and dev servers when asked |

> **The herdr app, not the herdr TUI.** From 0.15.0 forgerdr drives the herdr desktop app (`herdr-app`) and herdr-core (`hc`), which runs its terminals and agents. The app and the TUI run separate servers and share no agents, workspaces or plugins, so forgerdr supports one of them: the TUI version is 0.14.x and lives on the [`tui`](https://github.com/Gn0m0-dei/the-forgerdr/tree/tui) branch (see [Install](#install)).

## Install

First, [Claude Code](https://claude.com/claude-code), the [herdr app](https://herdr.dev/download/), which brings herdr-core (`hc`), and git, plus [Homebrew](https://brew.sh) on macOS. forgerdr lives in them: it never installs or removes them.

Then, on macOS or openSUSE Tumbleweed:

```bash
curl -fsSL https://raw.githubusercontent.com/Gn0m0-dei/the-forgerdr/main/install.sh | bash
```

It checks the prerequisites, shows every piece as here or to install and asks before it starts. Then it installs what is missing, a line a piece with a spinner meanwhile, and ends with a summary. What is here is left as it is, so running it again changes nothing. The pieces:

- the tools: jq, node, pnpm, `az` with the azure-devops extension, `gh`, `glab`, the [engram](https://github.com/Gentleman-Programming/engram) binary, the [codebase-memory-mcp](https://github.com/DeusData/codebase-memory-mcp) binary, the [OpenSpec](https://github.com/Fission-AI/OpenSpec) CLI and the Maple Mono NF font the forgerdr layout uses, with `~/.local/bin` put on the PATH in your shell's rc when it was not there;
- the plugins `forgerdr@the-forgerdr` and `azdo@azdospec`, with their marketplaces;
- forgerdr's look in the herdr app (the layout, the forge-night theme, the mod and the forge's alert sounds) and its status line, brought up to date on every run;
- the sign-ins it finds missing (`az login`, `gh auth login`, `glab auth login`), each asked first.

A piece that fails does not stop the rest: the summary names it, with the last lines it left in the log (`~/.local/state/forgerdr/install.log`, where the commands' own output goes). On openSUSE, sudo is asked once at the start, when zypper needs it. `NO_COLOR` turns the colours off. Another distro: install the pieces by hand.

Then open the herdr app (`ctrl-shift-l` switches to the forgerdr layout) and start Claude Code in one of its terminals. `/forgerdr:setup` checks every piece whenever you want and reports a table: engram server, the MCP servers reaching through the plugin, the herdr app and its optional keys, provider sign-ins, Claude Code settings, and the leftovers the plugin now replaces, the herdr TUI's forgerdr plugin among them.

To take it away:

```bash
curl -fsSL https://raw.githubusercontent.com/Gn0m0-dei/the-forgerdr/main/uninstall.sh | bash
```

It lists the pieces that are on the machine now, a tool you had before among them, and removes only the ones you tick; then it names whatever could not be removed. Claude Code, the herdr app, git and your data stay: `~/.claude`, engram's memories in `~/.engram`, forgerdr's settings, the app's settings and the sign-ins. `uninstall.sh` runs `install.sh --uninstall`, the one place that knows the pieces.

Local checkout instead of the marketplace: `claude --plugin-dir /path/to/the-forgerdr`.

Still on the herdr TUI: install forgerdr 0.14.x from the `tui` branch instead, `/plugin marketplace add Gn0m0-dei/the-forgerdr#tui` and then `/plugin install forgerdr@the-forgerdr`. Both branches name the marketplace `the-forgerdr`, so remove the other one first (`/plugin marketplace remove the-forgerdr`); the README on that branch covers its herdr TUI plugin and keys.

### Memory and MCP servers travel with the plugin

`mcp-servers.json` declares the four MCP servers the way of working depends on, so nothing is registered by hand: **engram** (through `bin/engram-mcp.sh`, which scopes the server to the memory project key), **codebase-memory** (the code graph), **context7** (official library docs; export `CONTEXT7_API_KEY` for a higher rate limit) and **chrome-devtools** (browser verification). The engram and codebase-memory binaries are the only pieces outside the plugin; `install.sh` brings them like any other CLI.

Memory lives in `~/.engram/engram.db` and in Claude Code's own memory directory. A new machine starts empty unless you copy both.

## What runs on every session

`hooks/session-start.sh` injects the four rule files, resolves the **memory project key** (the workspace root when the repository sits in a workspace, a parent with its own `.claude`, `CLAUDE.md` or `AGENTS.md`; the repository otherwise), starts the engram server if it is down, folds the per-directory projects engram used to create into that key, registers the session, and after a compaction brings the project's memory context back. The engram MCP server is started with that same key, so a workspace of four repositories is one memory, not four.

Two layouts work without configuration. One repository with its own `.claude/skills` and `CLAUDE.md`: Claude Code loads them. A workspace of several repositories with shared `.claude/skills` and `CLAUDE.md` at the workspace root, above the git tree where Claude Code does not look: the session start lists those skills with their paths and prints that `CLAUDE.md`, so the agent reads them when they apply, from the main checkout and from any worktree of it. The other way round, a session started at the workspace root gets the skills inside each repository listed by repository.

Sessions carry the number they were opened for. `review` and `worktree` start every agent with `FORGE_SESSION_TITLE` in its environment (`PR <id>: <title>`, `#<id> <title>`, the change name for an OpenSpec change without a work item, the branch slug for free text) and the session start hook sets it as the session title, the same as `/rename`: `claude --resume` lists it, the herdr app shows it on the terminal, and memory saved in that session mentions the number. `workitem` opens one titled tab per item (`bin/forge-session.sh`) unless the session is already titled for the single item given; outside the app, a session that gains a number is asked once to `/rename` itself.

`hooks/guard-bash.sh` refuses, before they run, the commands the standards forbid: a branch created tracking the shared base, `git reset --hard` or `--mixed`, a force push, `pkill -f` and `killall`, `git worktree remove` inside the herdr app (it would leave the worktree's space open on a folder that is gone; `bin/forge-worktree-remove.sh` closes the space first), and a commit or pull request that attributes the work to AI (a whole-line trailer or badge is stripped instead and the command runs clean). `hooks/scrub-unicode.sh` removes invisible Unicode (zero-width, bidi controls, tag characters, stray BOMs) from every file the agent writes and reports the exotic spaces it leaves alone. `hooks/graph-augment.sh` adds code-graph context to every Grep and Glob. `hooks/inbox.sh` puts Claude Code's permission dialogs, questions and plans in the herdr app's inbox as well, and sends a turn whose final message asks a question typed in the chat back to ask it with `AskUserQuestion` (The forgerdr layout, below); outside the app it does nothing. `hooks/flow.sh` records each `/forgerdr:<command>` typed in a session on the flow of the item it works, which the herdr app's forge floor shows (The forgerdr layout, below); the skills report what only they know through `bin/forge-flow.sh`, as `references/flows.md` says, and outside the app nothing is recorded. `hooks/engram-session.sh` closes the engram session on stop and captures subagent output. `hooks/worktree.sh` takes over Claude Code's own worktrees (`EnterWorktree`, subagents with `isolation: "worktree"`, `claude --worktree`): each one is a git worktree under `.claude/worktrees/<name>` on branch `worktree-<name>`, nested ones included, from the base `worktree.baseRef` asks for, with the ignored `.env*` files and the `.worktreeinclude` files copied; inside the herdr app it also opens as a space of its own that does not take the focus, which the app nests under its repository. When the session ends, the ones it created with no change, no commit and no agent at work in them are removed, their spaces closed and their branches deleted; the rest stay. Inside the app, when a session starts or ends, the spaces forgerdr opened for worktrees removed where no hook sees it (`git worktree remove` or `rm` from Bash or a terminal) are closed, unless an agent is still at work there or the session stands in one. Nothing it does throws work away: a worktree with uncommitted changes is never removed, not even when Claude Code asks, and a branch goes only while it still points where it started or is merged. Claude Code runs a plugin's `WorktreeCreate` hook for `claude --worktree` from 2.1.300 on, and never with `--worktree --tmux`; it reads `worktree.baseRef` from the settings files, not from managed settings or `--settings`. Background sessions, workflows and `remote-control` worktrees go through the hook too; only the subagent case has been run for real.

| Rule file | What it fixes |
|---|---|
| `rules/standards.md` | English in the repo, the user's language in chat and in comments, zero AI attribution, typing, style, error handling, everything the user must answer asked with `AskUserQuestion`, git and pull request conventions |
| `rules/communication.md` | Terse replies, verdict first, full prose only where clarity needs it (warnings, drafts, review findings) |
| `rules/build.md` | The lazy ladder: nothing → reuse → stdlib → platform → installed dependency → one line → minimal code |
| `rules/memory.md` | When to search, when to save, what to save, how to close a session |

## Skills

| Skill | What it does |
|---|---|
| `/forgerdr:setup` | Installs and verifies the environment. Idempotent. |
| `/forgerdr:help` | Prints the cheat sheet: commands, flows, settings, the herdr app keys. Answered by a hook, without spending tokens. |
| `/forgerdr:mode` | Shows or sets the spec mode, globally or per project. |
| `/forgerdr:spec` | Classifies the request (spike, bounded, architectural), asks what matters, presents the design and stops for approval. The spec mode decides where the design is kept. |
| `/forgerdr:plan` | Turns an approved design into bite-sized TDD tasks with exact files, interfaces and tests, kept where the spec mode says. |
| `/forgerdr:build` | Executes a plan in this session: red, green, refactor, ledger, verification before every claim, fresh-context review at the end. |
| `/forgerdr:ship` | Finishes a branch: fresh verification, rebase, reviewer agent, commit with permission, `push -u`, pull request with the work item linked. |
| `/forgerdr:debug` | Root cause before any fix: investigate, pattern, one hypothesis at a time, regression test proven red then green. |
| `/forgerdr:security` | Runs the security auditor on the diff or a module, has a fresh verifier challenge every critical or high finding, triages confirmed and needs-validation findings with you (in the herdr app's forgerdr layout, from a security session of its own parked behind its security view), fixes only what you pick. |
| `/forgerdr:research` | Cited research report: sub-questions, one researcher agent each in parallel, synthesis with confidence levels. |
| `/forgerdr:workitem [--auto] <item> [\| <item>...]` | Works items in the current clone, one titled herdr app session per item, separated by `\|` (several in new `Work items` tabs, as many panes to a tab as fit): a backlog item URL (bug, PBI, task, issue), an OpenSpec change or free text, as the spec mode says. Brief, reproduce in the browser, root cause, proposal, branch without tracking, pull request, client-facing comment; an OpenSpec change continues from its stage. Six gates, none skipped. |
| `/forgerdr:worktree [--auto] [--no-dev] <item> [\| <item>...]` | The same, each item in its own git worktree, opened as a herdr app space in the background: its branch (named by the spec mode, reused when it exists) from `origin/develop` (or the remote HEAD), the main clone's ignored `.env*` files and an uncommitted OpenSpec change copied over, a titled Claude agent running `workitem` in its first tab, the dev server on the first free `PORT` from 3000 in a second one (none with `--no-dev`). |
| `/forgerdr:review <url...>` | Each pull request, one or many, in a herdr app tab of its own, never the tab you launch it from: the review view, and beside it a titled Claude agent; a colleague's pull request runs `review-other`, your own runs `review-own`. |
| `/forgerdr:review-other <url>` | Reviews a colleague's pull request in this session: every finding explained, you pick, drafts in your language, nothing published without an explicit yes. |
| `/forgerdr:review-own <url>` | Handles the review comments on your own pull request in this session: fix, reply or question per thread, you pick, then pushes, replies and resolves. |

Providers are reached through their CLIs, never through MCP servers: `references/providers.md` holds the exact commands for Azure DevOps, GitHub and GitLab.

### Flow

`workitem` and `worktree` work in the manual flow unless `--auto` is passed.

| Flow | What happens after the brief |
|---|---|
| manual (default) | analysis, reproduction, root cause or proposal; the next command is suggested and you drive with `spec`, `research`, `plan`, `build`, `debug`, `security`, `ship` |
| `--auto` | the whole pipeline: a bug goes root cause → fix → security → ship; a backlog item goes spec (the item is the spec) → research when there are alternatives → plan → build → security → ship; an OpenSpec change goes from its stage (spec, plan or build) to the end, and one at its ship stage goes security → ship |

The gates hold in both: design approved before code, permission per commit, drafts before anything is published.

### Spec mode

The commands are always the same; a setting decides where the design and the tasks live. `/forgerdr:mode spec <value>` sets it globally, `--project` for the current workspace only; the value is printed at every session start. Stored in `~/.config/forgerdr/config.toml`. The herdr app's forge mode (below) sets it too, with `mode` (GitHub and GitLab keep the design in the chat) and `backlog`, the repository or project its work comes from when it is not the origin's.

| Value | Design and tasks live in | Backend |
|---|---|---|
| `chat` (default) | the conversation | nothing written; approval in chat |
| `openspec` / `openspec:<store>` | the repository's `openspec/`, or a registered OpenSpec store (a separate specs repository) | OpenSpec 1.x through its CLI: `new change`, artifacts from its own templates, `validate --strict`, `archive` on the branch before the pull request |
| `azure` | Azure Boards: a Feature, backlog items with Gherkin acceptance criteria, child tasks, progress comments | the [azdospec](https://github.com/Gn0m0-dei/azdospec) plugin when installed (forgerdr wraps `/azdo:propose`, `/azdo:apply`, `/azdo:archive`), forgerdr's own `az` commands otherwise |

The mode also decides what `workitem` and `worktree` take as an item (an OpenSpec change or a work item URL in `openspec`, a work item URL in `azure`, a URL or free text in `chat`) and how its branch is named: [`references/items.md`](references/items.md) and the standards' "Branch names". Several items are separated by `|`, and only by `|`.

In `azure`, branches follow azdospec's naming so `/azdo:apply` works on the branch forgerdr created instead of opening its own. In `openspec`, a work item's change is named `<id>-<slug>` and links the item; a bug that only restores specified behaviour creates no change.

The backlog may live in another Azure DevOps organization than the code, as when a client hosts the repository and another company runs the backlog. Nothing links across organizations, and a `#<id>` in a commit would link the item with that id in the client's organization, so such an item is named `EXT-<id>` in everything that stays in the repository: the branch (`feature/EXT-1234-login-button`), the commit footer (`Refs: EXT-1234`) and the pull request title, never with a link or a backlog URL. Where the backlog is lives in the clone's `.git/config` (`azdospec.organization`, `azdospec.project`), shared with azdospec and never committed: [`references/items.md`](references/items.md).

The gates do not move with the mode: no implementation before an approved design, no commit without permission, nothing published without a yes.

## Agents

Four subagents the skills dispatch for a fresh context, each limited to the tools its definition lists (inside the herdr app each one runs in a terminal of its own, see below):

| Agent | Dispatched by | Returns |
|---|---|---|
| `forgerdr:reviewer` | `build` (end of plan, or each task in agent mode), `ship` | findings graded critical / important / minor with file and line, verdict |
| `forgerdr:security-auditor` | `security` | findings traced from actor to effect: confirmed with severity, needs-validation, rejected; smallest fix and regression test; domain references under `references/security/` |
| `forgerdr:security-verifier` | `security`, per critical or high finding | an independent attempt to refute the finding: confirmed, downgraded or rejected |
| `forgerdr:researcher` | `research`, one per sub-question | cited answer with confidence |

Inside the herdr app no agent runs hidden inside the session. `hooks/agent-dispatch.sh` intercepts every Agent call and starts the agent as its own Claude session in a herdr-core terminal of its own, through your login shell so it gets your environment (a login `sh` with the session's `PATH` for a shell that is neither of the sh family nor fish, such as nushell), without taking the focus: in a tab of agents of its own, `agents · <session>`, which opens in the background next to the session's tab, so the session's pane is never split. Each next agent halves the largest agent pane there that keeps both halves at least 80×15, so they form an even grid, and once none can be halved the agent opens another tab of agents, which the next ones fill the same way. With `isolation: "worktree"` it is a pane of its worktree's space. A session with no pane of its own (a sub-agent) starts its agents as sub-agents, which the app lists under it in its Agents sidebar. It gets the agent's definition (its instructions, its model, no write tools when the agent has none) and accepts the folder trust prompt for it, and it sends its final report back with SendMessage, beginning with `Report from <agent>`. The app shows whether it is working, waiting for you or done, from what Claude Code reports; `hooks/agent-state.sh` keeps the agent's record and reminds an agent that ends a turn without reporting, and the turn that reports ends with `✅ DONE`. End a done agent whenever you like, or keep it to ask it something. The next pass of the same task (a fix pass, a second review of a reviewer's own findings) goes to the same agent: the session sends it with SendMessage to the agent's name, and `hooks/agent-message.sh` delivers it as a new task, or, when its terminal ended, reopens the agent under the same name resuming its Claude session (`claude --resume`) with everything it already read. Nested agents work the same way, under the agent that started them. Each one is a whole session, so it costs more than an in-process subagent. A fork, and every agent outside the app, runs in-process. When the session ends, the agents it started that are done are ended. Tasks of one plan still run sequentially: one branch, one worktree, one editor at a time.

## The herdr app

forgerdr talks to the herdr app through its two command-line tools: `herdr-app do` for the window (spaces, tabs, the focus) and `hc` for the terminals and agents in it. The fan-outs and the agent dispatch work only inside a terminal of the app (`HC_TERMINAL_ID` set); outside it, the worktree hook still makes and removes plain git worktrees. `forge-worktree.sh` and `forge-worktree-remove.sh` open and close spaces whenever the app answers, so the `forgerdr` mod runs them too, with no terminal of its own and no UTF-8 locale. New tabs and spaces open without taking the focus unless the command is about what you look at next (the first review tab, a `workitem` tab, a Security tab).

The scripts are plain bash over `herdr-app`, `hc` and `jq`:

```bash
bin/forge-worktree.sh  [--plan] [--repo PATH]... [--base BRANCH] [--dev COMMAND] [--no-dev] [--port-base N] [--auto] [--no-agent] [--branch NAME --title TEXT | --kind KIND --title TEXT] <item>...
bin/forge-review.sh    [--cwd PATH] [--mod NAME] [--no-agent] <pr-url>...
bin/forge-security.sh  launch [--cwd PATH] [--mod NAME] [--title TITLE] [--item ID] [--scope TEXT] [--report-to ADDRESS] [--no-agent]
bin/forge-session.sh   [--cwd PATH] [--no-agent] [--no-focus] --title TITLE <prompt>
bin/forge-session.sh   [--cwd PATH] [--no-agent] --group NAME --title TITLE <prompt> [--title TITLE <prompt>...]
bin/forge-worktree-remove.sh [--discard | --force] <path>
bin/forge-worktree-remove.sh --plan <folder>
bin/forge-setup-keys.sh [--review KEY] [--worktree KEY] [--remove]
bin/forge-update.sh     check|apply
```

`forge-worktree.sh` makes each worktree where the app keeps its own (`worktrees.directory` in the app's `settings.json`, `~/.herdr/worktrees` by default), so the app's Open and Remove worktree see them, and `forge-worktree-remove.sh` removes one the way the app does: its spaces of this machine closed first, its branch kept. It refuses uncommitted work and a space where an agent is at work; `--discard` throws the uncommitted work away and still refuses an agent at work, `--force` does both. The ignored env files are copied into a new worktree only where no symlink its branch carries stands in their way, so a branch cannot send them outside the worktree. What the scripts cannot guess (which repositories an item touches in a multi-repo workspace, which `dev:<app>` script of a monorepo) the Claude skills decide and pass as flags: the repositories, the dev command, and the branch and title of every item the script cannot name from a work item (any item in `chat`, a change in `openspec`). `--kind` and `--title` before an item name its branch without asking the provider, from the kind, the item's id (a URL, `#12`, `AB#12`, `12`, `EXT-12` for an item of an external backlog, or `""` for none) and the title. The kinds are Conventional Branch's: `feature`, `fix`, `chore` and `release` start from the base, `hotfix` from the production branch (origin's `main`, else `master`), and a release is named by its version, dots kept (`release/v1.2.0`). A name git would refuse (a title ending in `.lock`, say) is refused in the plan, and an item of an external backlog never reuses the branch of the repository's own item with the same number, nor the other way round. A `--repo` that is a worktree stands for its repository. Each dev server gets the first port from `--port-base` (3000) that nothing listens on. `--plan` says what a run would make (`forge-worktree.sh`: the branch, its folder, the base and the ref it starts from, the dev server and its port; `forge-worktree-remove.sh`: the worktree a folder is in, its branch and its uncommitted files) and makes nothing. They print one JSON line per worktree, tab or pull request.

`FORGE_CLAUDE_ARGS`, when set, adds its words to every `claude` the scripts and hooks start (for example `--plugin-dir <checkout>` or `--settings <file>` to try a change of the plugin before installing it).

### Keys

`bin/forge-setup-keys.sh` adds keys to the app's `keys.json` (`/forgerdr:setup` offers it): two that make the fan-outs work without a Claude session open, and, in a `layout:forgerdr` section that only the forgerdr layout reads, one for each of the forgerdr mod's buttons; a layout key you already use is left out, and named:

| Key (macOS; Ctrl+Alt on Linux) | What it does |
|---|---|
| `Cmd+Alt+P` | Opens a tab that asks for pull request URLs and runs `bin/forge-review.sh` |
| `Cmd+Alt+T` | Opens a tab that asks for items separated by `\|` and starts a Claude session running `/forgerdr:worktree` on them, which reads the spec mode |
| `Cmd+Alt+S` | In the forgerdr layout: Start work on the forge shown (`forgerdr.start`) |
| `Cmd+Alt+F` | In the forgerdr layout: the forge floor (`forgerdr.floor`) |
| `Cmd+Alt+I` | In the forgerdr layout: opens or closes the inbox (`forgerdr.inbox`) |
| `Cmd+Alt+L` | In the forgerdr layout: folds or unfolds the golem lanes (`forgerdr.lanes`) |
| `Cmd+Alt+M` | In the forgerdr layout: the forge's mode (`forgerdr.mode`) |
| `Cmd+Alt+/` | In the forgerdr layout: the smith's manual (`forgerdr.manual`) |

In the forgerdr layout, `START WORK` under the forge's gnome does both from a dialog, and more (see below). It keeps every other key, refuses a key you already use (`--review` and `--worktree` pick others), finds the installed plugin when the key runs so an update keeps it working, and `--remove` takes its keys away. Once `keys.json` is edited, the app treats it as yours and stops adding its new default keys to it.

### The forgerdr layout

forgerdr brings its own look for the app, drawn from the forgnome design: the `forgerdr` layout, the `forge-night` theme and the `forgerdr` mod, under `herdr/`. `bin/forge-herdr-install.sh` (`/forgerdr:setup` offers it) copies them into the app's home; `ctrl-shift-l` switches to the layout, and `ctrl-alt-shift-escape` always goes back to the app's own `main` layout. Across its top runs the forgerdr bar: a forge tab per repository, its main checkout and its worktrees together (a space outside git is a forge of its own), with its gnome and a badge of what its golems do (`!` when one waits on you, how many work, `✓` when one is done), the `+` that opens a space, `FLOOR`, which opens the forge floor over the window (below), `INBOX` with how many things wait on you (a click opens the inbox, below; while it is open the button's words light up and it runs down into the drawer, edged as the drawer is, as a tab opens into its panel) and the command palette with its key from `keys.json`. `START WORK`, under the forge's gnome in the sidebar (a hammer on the rail; also `Start work…` in a forge's menu, and `forgerdr.start` from a key or `herdr-app do forgerdr.start`), opens a dialog that starts the forge's work as its mode takes it, without typing a command.
```bash
bin/forge-herdr-install.sh [--dev [--watch]] [--remove] [--force] [--switch]
```

Run again, it updates what it installed and leaves what you changed, naming it (`--force` replaces it, keeping a copy beside it); `--remove` takes it away, except the theme, which any layout may use. `--dev` installs the checkout beside it as `forgerdr-dev`, a copy of the mod and a layout that uses it, and `--watch` keeps that copy in step with the checkout until Ctrl-C, so the app reloads the mod as you edit it: the app does not see edits through a link.

The mod draws with a kit of the design's pieces (`herdr/mods/forgerdr/kit/`: chips, key buttons, tabs, tree rows, pane headers, meters, the empty state, the toast) and the design's pixel art: 12×12 icons in one ink, gnome heads in parts (hat, face by eyes and mood, beard, accessory) and golems, as SVG layers under `img/`. `node herdr/tools/sprites.mts` generates them from the design's exports in `herdr/tools/design/`; a layer of fixed colours is drawn with `image()`, and one colour that changes (a hat, a theme tone) with `svg()`, which the app tints, so the art follows the theme. `test/herdr-sprites.test.sh` fails when `img/` drifts from the generator. The `gallery` role shows every piece and sprite on one page, to compare with the design: `herdr-app do tab.new --name gallery --mod forgerdr-dev --props '{"role":"gallery"}'`.

## Development

```bash
pnpm install
pnpm lint       # biome + shellcheck (install.sh, bin, hooks, test, herdr/tools)
pnpm test       # the pure functions, the hooks, and the scripts against fake hc and herdr-app (test/fakes.sh)
pnpm validate   # claude plugin validate .
pnpm typecheck:herdr  # the forgerdr mod against the type files the herdr app writes (skipped where it is not installed; runs on commit when herdr/mods changes)
```

The fan-out scripts and the agent dispatch are also exercised by hand inside the herdr app (`--no-agent` creates the topology without starting agents; `FORGE_CLAUDE_ARGS="--plugin-dir $PWD"` makes the agents load the checkout). Say in the pull request what you ran.
